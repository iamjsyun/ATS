# [보고서] Partial Class 기반 소스 파일 분리 설계 구조 분석 및 평가

## 1. 개요
현재 XTX 프로젝트의 핵심 서비스(XGatewayService, XTradePolicyService 등)는 FluentSeq를 활용한 상태 머신 구조를 가지고 있습니다. 이 구조를 partial class를 이용해 **상태 정의(States)**, **행위 로직(Actions/Methods)**, **핵심 인프라(Core)** 등으로 물리적 파일을 분리하는 전략에 대한 분석입니다.

## 2. 장점 (Pros)

### A. AI 컨텍스트 최적화 (AI-Friendly)
- **Token 절약**: AI가 특정 버그 수정이나 로직 변경을 수행할 때, 클래스 전체(수천 라인)를 읽지 않고 관련 파일(예: XGatewayService.States.cs)만 집중적으로 로드하여 토큰 소모를 획기적으로 줄일 수 있습니다.
- **분석 정확도 향상**: 파일 단위가 작아지면 AI의 추론 범위가 좁아져, 관련 없는 코드와의 혼동(Hallucination)이 줄어들고 코드 생성 품질이 높아집니다.

### B. 유지보수 및 가독성 (Maintainability)
- **관심사 분리 (SoC)**: 시퀀스의 흐름과 개별 상태의 세부 구현 로직을 물리적으로 분리하여, 전체 흐름을 파악하기 위해 수천 라인을 스크롤할 필요가 없습니다.
- **충돌 방지**: 협업 시 특정 상태 로직만 수정하는 경우 Git 충돌 발생 확률이 낮아집니다.

### C. 컴파일 및 빌드 가시성
- 파일명이 구체적(예: .Workflow.cs, .Validations.cs)이므로 솔루션 탐색기에서 해당 모듈의 전체적인 구조를 한눈에 파악하기 유리합니다.

## 3. 단점 및 약점 (Cons)

### A. 파일 관리 오버헤드
- **파일 개수 폭증**: 서비스가 늘어날수록 파일 수가 기하급수적으로 증가하여 프로젝트 구조가 복잡해 보일 수 있습니다.
- **이동성 저하**: 특정 필드가 어디에 정의되어 있는지 찾기 위해 여러 파일을 오가야 할 수 있습니다. (IDE의 F12 기능으로 보완 가능)

### B. 상속 및 인터페이스 구현의 파편화
- partial class는 여러 파일에 흩어져 있어도 하나의 클래스이지만, 너무 쪼개질 경우 생성자 주입(DI)이나 초기화 로직이 어느 파일에 있는지 혼동될 수 있습니다.

## 4. 평가 및 추천 전략

### 종합 평가: **[매우 권장 (AI 협업 환경에서 필수적)]**
단순한 파일 수 증가의 불편함보다, **AI가 컨텍스트를 정확하게 파악하고 비용 효율적으로 코드를 관리**할 수 있다는 점이 현대적인 개발 환경(Cursor, Gemini CLI 등 사용 시)에서 훨씬 큰 이점을 가집니다.

### 추천 분리 패턴 (Standard)
다음과 같은 명명 규칙으로 분리하는 것을 추천합니다:

1.  {ClassName}.cs: 필드, 생성자, 속성, DI 설정 (Core)
2.  {ClassName}.Sequence.cs: FluentSeq 설정 및 상태 흐름 정의 (Workflow)
3.  {ClassName}.Methods.cs: 시퀀스에서 호출하는 내부 private/protected 메서드들 (Logic)
4.  {ClassName}.Events.cs: 외부 이벤트 핸들러 및 알림 로직 (Events)

---

### [결론]
본 구조는 AI 시대의 **"Micro-Context Management"** 전략에 부합합니다. 특히 XTX 프로젝트처럼 상태 기반 로직이 많은 경우, AI가 특정 상태(State)만 타켓팅하여 수정하는 것이 훨씬 안전하고 빠릅니다. 

사용자님의 제안대로 **클래스명은 유지하되 partial class로 분리하는 구조**를 프로젝트의 표준 리팩토링 가이드라인으로 채택할 것을 제안합니다.
